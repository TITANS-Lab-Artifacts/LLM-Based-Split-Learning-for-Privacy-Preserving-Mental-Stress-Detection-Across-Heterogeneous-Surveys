## What this is

Institutions collect a lot of mental health survey data, but they cannot pool it. Privacy rules keep the records siloed, and every institution uses a different survey instrument, so the feature spaces do not line up either. This work addresses both problems at once.

Each survey row is serialized into a natural-language description, so "sleep duration: less than 5 hours" carries its own meaning instead of sitting at a fixed position in a vector. Surveys that ask about similar things in different ways then land in a shared representation. A LoRA-adapted LLaMA-3.2-3B-Instruct acts as the semantic encoder, and it is split between client and server: the client keeps the tokenizer, a LoRA-adapted embedding, and a small projection head, while the transformer trunk and LM head sit on the server. Raw responses never leave the institution. Only cut-layer activations and their gradients cross the boundary.

Headline numbers reported in the paper:

- Average ANLS of **0.708** across a 3x3 grid of data-volume imbalance and schema heterogeneity, using at most 2,000 training samples spread over 10 clients.
- Beats a FedAvg federated baseline (0.687 average) in **eight of nine** settings.
- Cuts per-client computation by roughly **three orders of magnitude** versus federated learning: 3.68M trainable parameters and about 1.3 GB on the client, against a full-model 15 to 25 GB FL client.
- Generalizes to unseen survey datasets from a small training pool.

Four LLM configurations are compared (zero-shot, few-shot, centralized LoRA, split learning), plus a supervised FT-Transformer on the tabular version of the same data as a non-LLM reference. Everything is scored with ANLS (Average Normalized Levenshtein Similarity) through one shared normalization routine, so the numbers are comparable across methods.

**Privacy model.** The claim is data locality: original responses, identifiers, and labels stay on the client. The paper does not claim the intermediate tensors resist reconstruction, and defending against model-inversion attacks is out of scope. Nothing in this repository implements differential privacy or activation obfuscation.

None of the four raw datasets were collected by us. See section 2.1 for sources and credit.

### 2.2 What is built from them

Each source is converted into `instruction` / `input` / `output` JSONL rows. Identity attributes (age, gender, race, country, state, timestamps) are dropped at conversion time and never reach the model.

| Short name | File | Built from | What the model predicts |
|---|---|---|---|
| OST | `mh_tech_dataset.jsonl` | OSMI, 9 survey files merged | Treatment seeking, workplace support, and related outcomes |
| D-42 | `mh_dass_dataset.jsonl` | DASS-42 responses | Depression, anxiety, stress severity levels and clinical-level flags |
| SD | `mh_student_dataset.jsonl` | Student Depression Dataset | Depression status, suicidal thoughts, sleep adequacy, stress burden, lifestyle risk |
| MHD | `mh_general_dataset.jsonl` | Mental Health Dataset | Treatment, growing stress, coping struggles, work interest, social weakness, care options |

Each respondent row produces several samples, one per outcome (7 for OST, 7 for D-42, 5 for SD, 6 for MHD), so the model learns a survey's multiple distress outcomes rather than one fixed input-to-label mapping. The outcome being predicted is stripped from the input to prevent leakage, and exact `(input, output)` duplicates are dropped before any split.

Two mixes are built on top of these, giving three levels of schema heterogeneity:

| Short name | Files | Contents |
|---|---|---|
| (per dataset) | `train_/test_mh_tech_dataset.jsonl` etc. | Homogeneous: each of the four datasets on its own |
| MHg | `train_/test_mod_hetero.jsonl` | Moderate heterogeneity: OST + SD merged |
| Hg | `train_/test_hetero.jsonl` | Full heterogeneity: all four datasets merged |

500 samples are held out as the test set for each of the six splits (seed 42).

A single JSONL row looks like this:

```json
{
  "instruction": "How severe is this person's stress according to their symptom scores?",
  "input": "Symptom responses - Q2 (awareness of dryness of mouth): considerably ... | Personality - ... | Education: high school | ...",
  "output": "Based on the non-stress symptom responses and personality profile, this person's stress severity is: Severe (score: 29/42)."
}
```

Every loader resolves field names through aliases (`instruction`/`question`/`prompt`, `input`/`context`/`text`, `output`/`answer`/`label`), so datasets with slightly different keys still work.

## 3. Code files

### 3.1 Data preparation (`data_preparation/`)

All paths are resolved relative to the repository, so the scripts run from any working directory.

| File | What it does |
|---|---|
| `convert_osmi.py` | Merges the nine OSMI survey files in `data/raw/OSMI/`, strips HTML/markdown from column names, maps them to canonical names, and writes `data/processed/jsonl/mh_tech_dataset.jsonl`. One sample per available outcome. |
| `convert_dass42.py` | Recodes the 42 items from 1-4 to the standard 0-3 scale, sums the three subscales (14 items each), applies the standard DASS-42 severity thresholds, and writes `mh_dass_dataset.jsonl` with seven outcomes per respondent. |
| `convert_student.py` | Converts the Student Depression Dataset to `mh_student_dataset.jsonl` with five outcomes per row. |
| `convert_general.py` | Converts the Mental Health Dataset to `mh_general_dataset.jsonl` with six outcomes per row. |
| `split_text_datasets.py` | Splits each JSONL into train/test (500 test samples each), then builds the `mod_hetero` and `hetero` mixes. Writes to `data/processed/text/`. Seed 42. |
| `prepare_tabular.py` | The CSV equivalent for the FT-Transformer. Splits each raw source into `train_*.csv` / `test_*.csv` and builds the two mixes. When mixing, only columns present in every participating dataset are kept. Uses different test sizes per dataset (100 for OSMI up to 2,000 for MHD). Writes to `data/processed/tabular/`. |

### 3.2 Split learning (`experiments/`)

| File | What it does |
|---|---|
| `config.py` | Every hyperparameter and path in one place. Defines the 3x3 experimental grid, the LoRA settings, the cut-layer bottleneck width, and the two-GPU device assignment. Reads data from `data/processed/text/`. |
| `data_partition.py` | Pure Python, no torch. Shards the training rows across ten clients according to the volume asymmetry level, and picks which dataset file feeds the clients based on the schema level. |
| `model_client.py` | The lightweight client. Holds a frozen copy of the LLaMA embedding table, a LoRA delta on top of it, and a two-layer residual projection head. The head is zero-initialized so the cut starts out exactly equal to the raw embedding. |
| `model_server.py` | The server. Loads LLaMA-3.2-3B, applies LoRA to the whole transformer trunk, and runs forward from `inputs_embeds` rather than token ids. |
| `split_train.py` | The training loop. Client forward, detach at the cut, ship to the server GPU, server forward and backward, ship the cut gradient back, client backward. One optimizer spans both sides. |
| `evaluate.py` | Batched greedy generation through the split pipeline with left padding, then ANLS scoring. |
| `sl_data.py` | Tokenization and collation. If prompt plus answer exceeds the sequence limit, it trims the prompt from the middle and always keeps the full answer, so long DASS rows are never dropped. |
| `anls.py` | The scoring metric. Shared with every other experiment so results stay comparable. |
| `progress.py` | Progress bars for tokenization, training, and evaluation. |
| `run_experiment.py` | Runs one cell of the grid end to end and writes `experiments/result_split/<volume>__<schema>.json`. |
| `run_all.py` | Sweeps all nine cells, skips cells whose result file already exists, and writes `summary.json` plus `summary.csv`. |
| `run_generalization.py` | Trains one model on `symmetric x high`, then evaluates that same model against every `test_*.jsonl` file and writes `result_split_generalization.csv`. |

**How the two factors work.** Factor A is partner data volume asymmetry: `symmetric` gives every client an equal shard, `moderate` uses the fixed split `[25, 15, 12, 10, 10, 8, 7, 6, 4, 3]` percent, and `high` gives client 0 sixty percent with a floor of thirty rows for everyone else. Factor B is schema heterogeneity, realized by which file feeds the clients: `homogeneous` uses the tech dataset, `moderate` uses the tech-plus-student mix, `high` uses the all-four mix.

**Where the cut sits.** Right after the client projection head and before the transformer trunk, so the client is as light as possible and the entire decoder stack lives on the server.

### 3.3 Centralized and prompting baselines (`experiments/`)

| File | What it does |
|---|---|
| `finetune_llama.py` | LoRA fine-tuning of LLaMA-3.2-3B-Instruct on one train/test pair, followed by ANLS evaluation. The adapter is not saved. |
| `finetune_openbio.py` | Same, for `aaditya/Llama3-OpenBioLLM-8B`. |
| `run_all_centralized_lora.py` | Batch-runs both fine-tuning scripts over all six dataset pairs. Renames each output to `results.<model>.json` so the two models do not overwrite each other. |
| `Zero_Shot.py` | Zero-shot ANLS evaluation of an instruction-tuned model on a test JSONL. |
| `Few_Shot.py` | Few-shot ANLS evaluation. For each test row it picks training examples whose instruction starts with the same five words, falling back to random examples when there are not enough matches. |
| `run_inference_all.py` | Batch-runs zero-shot and few-shot for both models across all six pairs, with logging and skip-if-exists. |

### 3.4 Tabular reference model (`experiments/ft_transformer/`)

## 4. The metric

ANLS is computed in `experiments/anls.py` and works in four steps:

1. Pull the core answer out of both the generated text and the expected text. "Yes, this worker has sought treatment" becomes "yes", "very high risk" becomes "extremely severe", and so on.
2. Normalize both: lowercase, strip accents, drop articles and punctuation, collapse whitespace.
3. Compute normalized Levenshtein similarity between the two.
4. Anything below the 0.5 threshold scores zero. Adjacent severity levels get 0.5 partial credit. ANLS is the mean over all test rows.

Do not change the normalization if you want your numbers to line up with the ones below. Every experiment in the repository uses this routine.

## 5. Requirements

```bash
python -m pip install -r requirements.txt
python -m pip install flash-attn   # optional; the code falls back to SDPA attention if it is missing
```

`requirements.txt` lists the packages the code imports (PyTorch, Transformers, PEFT, Accelerate, scikit-learn, pandas, NumPy, Matplotlib, openpyxl, packaging). The exact versions used for the paper were not recorded in the original project, so the file gives no version pins.

Hardware stated by the authors: two NVIDIA RTX 6000 Blackwell GPUs (96 GB each) and 32 GB RAM. The split learning code puts the server trunk on `cuda:0` and the client front-end on `cuda:1`, and falls back to one GPU or CPU if fewer are present. The 8B OpenBioLLM runs need considerably more memory than the 3B LLaMA runs.

Model access: `meta-llama/Llama-3.2-3B-Instruct` is gated on Hugging Face. Accept the license and run `huggingface-cli login` before your first run.

### Where the client / server split falls, and what it costs

| Side | Frozen base | Trainable params | Compute per step | VRAM (train) |
|---|---|---|---|---|
| SL client | ~0.39B | 3.68M | ~0.08 TFLOPs | ~1.3 GB |
| SL server | ~3.21B | 24.31M | ~158 TFLOPs | 15-25 GB |
| FL client (each) | ~3.21B | 24.31M | ~158 TFLOPs | 15-25 GB |
| FL server | 0 | 0 | ~0 | ~0 (CPU) |

LoRA brings trainable parameters to roughly 0.75% of the model. The client's share is 0.114% of the 3.21B total, which is where the three-orders-of-magnitude compute claim comes from. These are the paper's order-of-magnitude estimates, not measured wall-clock figures.

## 6. How to run

Run the commands from the repository root unless a step says otherwise.

### Step 1: build the JSONL datasets from the raw data

```bash
python data_preparation/convert_osmi.py
python data_preparation/convert_dass42.py
python data_preparation/convert_student.py
python data_preparation/convert_general.py
```

Output: `data/processed/jsonl/mh_{tech,dass,student,general}_dataset.jsonl`.

### Step 2: split and mix

```bash
python data_preparation/split_text_datasets.py   # -> data/processed/text/   (JSONL splits for all LLM runs)
python data_preparation/prepare_tabular.py       # -> data/processed/tabular/ (CSV splits for the FT-Transformer)
```

The six JSONL train/test pairs need about 2 GB of disk space.

### Step 3: prompting baselines

```bash
cd experiments

# one run
python Zero_Shot.py --test ../data/processed/text/test_mh_tech_dataset.jsonl --model meta-llama/Llama-3.2-3B-Instruct
python Few_Shot.py  --train ../data/processed/text/train_mh_tech_dataset.jsonl \
                    --test  ../data/processed/text/test_mh_tech_dataset.jsonl --n_few 10

# the full sweep: 2 models x 6 pairs x {zero, few}
python run_inference_all.py
python run_inference_all.py --models llama --modes few_shot   # narrower
python run_inference_all.py --dry-run                          # print commands only
```

Results are written to `data/processed/text/results/` (next to the test files). Logs go to `experiments/inference_logs/`.

### Step 4: centralized LoRA fine-tuning

```bash
cd experiments
python finetune_llama.py --train ../data/processed/text/train_mh_tech_dataset.jsonl \
                         --test  ../data/processed/text/test_mh_tech_dataset.jsonl --n_train 2000
python finetune_llama.py --train ../data/processed/text/train_mh_tech_dataset.jsonl \
                         --test  ../data/processed/text/test_mh_tech_dataset.jsonl --n_train 200 --n_test 50   # smoke test

# both models over all six pairs (paper setting)
python run_all_centralized_lora.py --n_train 2000
```

Results land in `experiments/results/<train_stem>__<test_stem>/results.<model>.json` when run from `experiments/`. Logs go to `experiments/run_logs/`. This runner re-runs every pair unless you pass `--skip-existing`.

### Step 5: split learning

```bash
cd experiments

# one cell of the grid, at the paper's setting
python run_experiment.py --volume symmetric --schema homogeneous --max_sample 2000

# all nine cells (skips cells that already have a result; --force to redo)
python run_all.py --max_sample 2000

# the generalist run: train once on symmetric x fully heterogeneous with a
# 10,000-sample pool, then evaluate on every test file
python run_generalization.py --max_sample 10000 --eval_batch 64
```

The `--max_sample 2000` matters. The 3x3 grid in the paper caps the pool at 2,000 samples split across the 10 clients; `config.MAX_SAMPLE` is 10,000, which is the generalist setting. Running `run_all.py` without it uses 10,000 and will not reproduce Table IV.

Output goes to `experiments/result_split/`: one JSON per cell, plus `summary.json`, `summary.csv`, and `result_split_generalization.csv`/`.json`.

With `--save_model`, the trained pieces are written to `experiments/result_split/saved_models/<train_stem>__<test_stem>/`: the server LoRA adapter, a `client_state.pt` holding the embedding LoRA and projection head, the tokenizer, and a `manifest.json` with everything needed to rebuild the client. The frozen base model is not saved; it is reloaded from the Hugging Face Hub.

### Step 6: tabular reference

```bash
cd experiments/ft_transformer
python run_ft_transformer.py --epochs 30 --batch 256          # all six CSV pairs in data/processed/tabular/
python ft_transformer.py --train ../../data/processed/tabular/train_student.csv \
                         --test  ../../data/processed/tabular/test_student.csv   # one pair
```

Models and per-pair results are written to `data/processed/tabular/` and `data/processed/tabular/results/`; the batch summary is `data/processed/tabular/results/batch_summary.json`.

### Step 7: figures

```bash
cd figures
python fig1_ft_performance.py
python fig4_generalization.py
python fig5_general_gain_heatmap.py
python fig6_backbone_gain_heatmap.py
python tabular_figures.py          # supplementary, written to figures/tabular_figures/
```

## 7. Reported results

These numbers are from the result files of the paper's runs, which are not included in this repository. Use them to check a rerun.

### 7.1 LLM methods, ANLS

| Dataset | Zero-shot LLaMA | Zero-shot OpenBio | Few-shot LLaMA | Few-shot OpenBio | LoRA LLaMA | LoRA OpenBio |
|---|---|---|---|---|---|---|
| MHD (general) | 0.210 | 0.257 | 0.258 | 0.136 | 0.444 | 0.427 |
| OST (tech) | 0.336 | 0.370 | 0.316 | 0.280 | 0.761 | 0.753 |
| D-42 (DASS) | 0.097 | 0.155 | 0.170 | 0.164 | 0.788 | 0.776 |
| SD (student) | 0.274 | 0.333 | 0.336 | 0.393 | 0.664 | 0.657 |
| MHg (mod hetero) | 0.302 | 0.314 | 0.353 | 0.375 | 0.631 | 0.650 |
| Hg (full hetero) | 0.155 | 0.196 | 0.238 | 0.226 | 0.702 | 0.693 |

LLaMA is `meta-llama/Llama-3.2-3B-Instruct`, OpenBio is `aaditya/Llama3-OpenBioLLM-8B`. Few-shot used 10 examples per prompt.

LLaMA averages 0.229 zero-shot and 0.279 few-shot, so prompting alone does not map heterogeneous surveys onto distress labels. Per-dataset LoRA lifts that to 0.665. OpenBioLLM-8B reaches 0.659; its edge shows up mainly in zero-shot and mostly disappears after adaptation, so LLaMA stays competitive at roughly a third of the size.

## 8. Things worth knowing before you rerun anything

- **The federated baseline code is not included.** The FedAvg numbers in Table IV come from a run whose training script is not part of this project. Anyone reproducing the FL row will need that script.
- **Respondent-level splitting is not implemented in this splitter.** The paper states that all splitting is done at the respondent level, so no respondent appears in more than one split. `data_preparation/split_text_datasets.py` does not do this: `split()` shuffles the flat sample list and slices it, and the JSONL rows carry no respondent identifier to group on. Since each respondent yields 5 to 7 samples that share most of their input text, samples from one respondent can land in both train and test. Deduplication on `(input, output)` is implemented in all four converters, but it removes identical samples, not same-respondent ones. This should be resolved, or the paper text corrected, before release.
- **`MAX_SAMPLE` overrides `--frac`, and its stored value is the generalist setting.** `partition_clients` applies `max_sample` first and only falls back to `frac` when it is `None`. `config.MAX_SAMPLE` is 10,000, the generalist run's pool, not the 2,000 used for the 3x3 grid. Pass `--max_sample 2000` for the grid.
- **Diagnostic flags in `config.py`.** `DIAGNOSTIC_IDENTITY` bypasses the client head and must stay `False` for real runs. `DIAGNOSTIC_GRAD_STATS` is `True` and prints cut activation and gradient statistics once per epoch.
- **No `GradScaler` in split training.** This is deliberate. The cut gradient is read off the server tensor and shipped to the client, and a scaler would scale it on one side without unscaling on the other. The LoRA parameters are FP32, so plain FP16 is stable here.
- **Resume behavior.** `run_all.py` and `run_inference_all.py` skip work whose output file already exists; pass `--force` or `--no-skip-existing`, respectively, for a fresh run. `run_all_centralized_lora.py` only skips when given `--skip-existing`.
- **Reproducibility of the data pipeline.** Running steps 1 and 2 on the included raw data reproduces, byte for byte, the train/test JSONL and CSV splits used in the original project.
